# ADR-0004：持久化多任务调度与自动流水线

- 决策状态：PROPOSED；实施未开始。
- 日期：2026-09-22；模式：Write ADR。
- 原始需求：[U1 对齐](sources/20260922-automated-production-workspace.md#u1)、[U2 禁改](sources/20260922-automated-production-workspace.md#u2)、[U3 自动化](sources/20260922-automated-production-workspace.md#u3)。关键原文：“整个任务支持多线推进，多任务，自动执行，多管理”。
- 交付状态唯一来源：[阶段计划](automation-workspace-plan.md)。

## Context and Structural Baseline

基线 `6cc8174`：`api.ts` 464 行，以进程内 `workflowFlights` 串行同会话写入，`run-next/run-all` 等待执行结果再响应；`runner.ts` 731 行，已有依赖、校验和阶段检查点；`nativeMediaStages.ts` 1791 行，镜头循环等待生成、缓存和校验。`store.ts` 1378 行，通过单进程 writeQueue 串行保存完整 JSON。当前存储不能直接由多个 worker 进程共同写入。

因此“后台执行”首先是脱离 HTTP 请求生命周期与持久恢复，不等于立即拆成多进程或分布式队列。不得把新调度职责继续堆到 `index.ts`（7621 行）或现有 runner 大函数中。

## Discussion Basis and Decision

产品方向与报价禁改已确定。以下为 agent-proposed 推荐方案，转入执行前须接受该 ADR；首阶段验证存储和恢复协议，未通过不开放并发。

### 1. 持久运行与单写入者

- 引入 Run、WorkItem、Attempt、Dependency、Event；每个都带 owner/session 身份。业务成果仍由现有 artifact 合同定义。
- Run 记录执行意图、目标停止点、调度策略；WorkItem 对应一个阶段或可独立处理的资产/镜头；Attempt 是一次不可混淆的执行尝试。
- 推荐 SQLite 控制记录仓库（运行状态、事件、幂等键、租约、待投影记录同事务），现有 JSON 成果暂不整体迁移。引擎先嵌入现有服务，以独立异步循环运行，CinemaStore 保持唯一写入者；不允许另一进程直接写 JSON。
- SQLite 适配器需先验证当前 Node/Windows、打包和备份可行性，不预设未安装依赖可用。方案成本、驱动兼容或跨存储恢复未通过时，阶段 P0 保持未通过，修订提案，不能以裸 JSON 队列冒充同等级保证。
- 不做分布式事务假设：结果先写内容寻址文件并落控制事务，创建投影意图；单写入者幂等写 CinemaStore（operationId + 预期 revision），成功后才发布成果可用事件。JSON 已写但确认丢失时用标记回读确认，不重复增版本。投影失败显式显示“结果待保存”，禁止后续调度；不提前宣布完成。

### 2. 并发与公平性

- 多项目可独立推进；单项目只能调度 canonical 依赖已满足的节点。九步仍是用户导航，不能为“多线”凭空增加业务支路或绕过确认关卡。
- 首先并行已有独立资产/镜头；依赖前镜头尾帧、参考视频或其他产物的工作严格等待对应版本就绪。按稳定镜头 sequence 展示与拼接，完成顺序不改变故事顺序。
- 全局、owner、session、Provider 分层限额；有队列上限与公平轮转。可调优先级只影响未开始工作，不抢占在途请求；等待时间参与优先级防饥饿。超限返回明确原因及恢复途径。
- 初始并发默认 1，测试通过后按记录的压力数据逐层提高；生产值另行验收，不能把 FrameFlow 的 worker 数当作本项目容量证明。
- 同一输出版本只允许一个有效发布者；幂等键包含 owner/session/目标/输入版本/操作意图。双击、断网重放返回同一 Run；主动重试生成新的 Attempt，不抹去历史。

### 3. 自动推进与编辑竞争

- 单步运行、自动推进到下一个确认点、继续已确认流程共享同一调度器；必要的课程导入/资产确认规则保留。用户确认后可继续先前启动的自动计划，不自动创建无限期新计划。
- 自动计划钉住已保存输入和确认版本；运行期间的新编辑属于新草稿。编辑相关节点时提供编辑占用状态，冻结该节点尚未启动的自动推进；已提交请求继续跟踪其旧版本，不偷偷换输入。
- 保存改变血缘时：旧结果保留为历史，受影响未开始项标记待重算；用户使用“保存并继续”才明确恢复受影响分支。无关项目与分支继续运行。
- worker 只复用原有阶段执行器、引用快照、Provider taskId 和重试规则；已有 QUOTE 视为不透明的兼容阶段，不改其实现、载荷、呈现和确认合同。

### 4. 可见状态与控制语义

内部状态建议：QUEUED、RUNNING、WAITING_INPUT、PAUSE_REQUESTED、PAUSED、CANCEL_REQUESTED、CANCELLED、RECONCILING、FAILED、SUCCEEDED；前端映射为“等待执行／执行中／待确认／正在暂停／已暂停／正在停止／已停止／正在核对／失败／完成”。

- 暂停：立即阻止调度新工作，已在途项到安全边界后才标已暂停；不能伪装成 Provider 已暂停。
- 停止后续：取消未提交项，在途项继续收集结果；不等同远端取消。
- 取消在途：只在适配器有真实能力时提供，收到终态前显示取消请求中；不承诺退费，也不修改计费策略。
- 重试失败项：成功结果可复用，输入版本必须匹配。外部受理未知时进入核对状态，禁止自动再 POST；租约过期只代表需要恢复核对，不代表可以重发。
- 服务重启后先恢复台账、投影和已知任务轮询，再调度新工作；浏览器关闭不发取消。全局停止/重启不可丢失先前暂停意图。

## Module Ownership

建议新建 `src/server/productionRuns/`，分离 repository、scheduler、recovery、projector、api、events；共享合同放 `src/shared/productionRuns.ts`。现有 api 仅适配，runner 保持阶段职责；媒体执行提取单项适配器而非把循环并发直接塞回大函数。单模块若超约 400 行或同时负责路由/调度/存储，应在审查中说明或拆分，不压缩代码隐藏规模。

## Alternatives and Consequences

- 只加 Promise.all 与前端任务卡：成本低，但无持久调度和取消语义，拒绝作为最终方案。
- 完整迁移所有成果到数据库：一致性更简单，但范围大；本轮不作为默认，除非 P0 证据要求重新决策。
- Redis/多进程队列：适合横向扩容，当前 JSON 单写入者尚未解除；延后，不把基础设施数量当体验提升。
- 推荐方案需承担跨存储投影恢复、事件保留和调度运维成本；不宣称外部副作用 exactly-once。

## Compatibility, Rollback and Release

新增异步运行 API 返回已持久化 runId；旧同步 API/CLI 作为等待同一 Run 的兼容适配器，禁止两套执行引擎并行提交。旧未完成会话保持可读，原中断记录不推断为可自动恢复的新任务。开关回退前停止派单并处理在途任务；禁止在运行台账尚有活跃任务时切回旧引擎。数据库/媒体备份与恢复演练使用合成数据；生产迁移、部署及付费验证均不在本轮授权内。
