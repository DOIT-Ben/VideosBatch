## ⚠️ 重要教训：computed 指纹对拍**必须带阳性对照**

本轮写了 `output/shots/cmp.mjs`：对**整个 DOM 每个元素**的 17 项 computed 属性做哈希指纹
（并整页截图），在「已删版」与 `git show HEAD:` 换回的「原版」两套 CSS 下各跑一次。
9 步 studio（216 元素）+ canvas 编辑器（660 元素、24 个 flow 节点）**指纹逐项全等**，
截图最大偏差 0.107%。

**但第一次阳性对照差点骗过我**：我把 `--vbs-v2-accent` 改成 `#ff0000` 再跑，指纹**纹丝不动**。
当时有两种解释——(a) Vite 在服务缓存 CSS，那前面的「一致」就全是假的；(b) 该 token 到不了
被测属性。做了两件事才分清：
1. 直接 HTTP 取 Vite 服务的 CSS（`/src/client/styles.css?direct`），确认
   `media-lightbox-backdrop` 已消失、`lightbox-backdrop` 在 → **Vite 确实在吐新文件**；
2. 换成改 `--vbs-v2-canvas` / `--vbs-v2-text`（必然进 backgroundColor/color），
   并**先用 HTTP 确证 Vite 已吐出新值**，再跑 → 指纹立刻变（studio `38dd550a→b3f639c4`、
   canvas `eb926555→9d519d07`）。

结论两条，都是硬规矩：
- **凡「零变化」的结论，必须先有「阳性对照能变」才有意义**，否则无法区分「真的没变」和
  「根本没读到新文件 / 采样点选错了」。
- 对比前后两版文件时，**要顺手验证 dev server 实际服务的内容**，别假设改了文件 HMR 就吃到。
- 附注：`--vbs-v2-accent` 之所以改不动，是因为它的可见消费者（`.vbs-primary` 等）最终
  被 V2 层覆盖或用的是 `accent-deep` / `accent-soft`——这也再次印证「僵尸声明」的存在。

stderr 里这两行 shim 报错是**噪音**，不代表 node 进程有问题（进程本身照常监听）。
判定服务是否真起来，用 `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5173/`（返回 200），
不要依赖当时坏掉的 netstat/grep 管道。

## 用户上手时的三个疑问：新建任务 / 任务管理 / 「生成不了」

### ① 「新建任务」入口 = `/gallery`，但工作台里够不着

### ② 「生成不了」= 项目跑在 **fake 模拟模式**，不是坏了

## 「卡」的实测结论 + 后台服务会被回收

**② 真正的卡在「冷启动首屏」**（`output/perf-probe.mjs` 实测，session `ses_a6f10899`）：

|---|---|---|---|
| `/gallery` 第 1 次（冷） | **13905ms** | 119ms | 13896ms |
| `/gallery` 第 2 次（热） | 105ms | 24ms | 96ms |
