## ADR-0001 深度复审（大哥：「在深度审查一下是否对齐？检查一下。」）

方法：不信 ADR 自述，直接读 FrameFlow `bbb17414` 的 contracts/bounded-response/
newapi-h3-dedicated{reference-media,response,request,transport}/execution-payload/
reference-plan/video-creation-prompts{registry,loader} 逐行对照本仓实现。结论落
ADR §11。**门禁证据全部复核通过，但挖出 3 条本轮未覆盖的偏差**：

- **D1【高·方向危险】轮询阶段「任务失败」被判 `NOT_CHARGED`**（`newApiH3Video.ts:446-451`）。
  FrameFlow `response.ts:247` 是 `explicitBillingResult ?? (status==='completed' ? 'CHARGED'
  : 'UNKNOWN')` —— **任务受理后从不推断未计费**，`NOT_CHARGED` 只出现在提交前的本地校验
  （`request.ts:9,20`、`transport.ts:18`）。此格 `taskId` 已存在＝任务已被受理，判"未扣费"
  会诱导重提 → 重复计费；现由 `retryable:false` 兜住自动重试，但按 billingResult 对账的下游会判错。
  **连带**：spec §8.5 正文（2508 行）已把这条错规则固化，而**同文件验收标准（2559 行）只列了
  四类分层、不含这一格** → spec 正文与自身验收标准不一致；且 §8.5 同一条里"轮询失败→UNKNOWN"
  与"任务失败→NOT_CHARGED"出自同一个轮询循环，自相矛盾。
  **两个次级缺陷**：① 不读 Provider 显式 `billing_result`（FrameFlow `response.ts:64-65` 有
  schema，`:235/:247` 是"Provider 说了算、本地推断兜底"）；② 成功路径只返回 `mediaUrl: string`，
  不产生"已计费"证据（FrameFlow 成片拿到时 UNKNOWN 升格 CHARGED，`response.ts:306`）。
- **D2【中·只做一半】P2 的"版本化"没有可回读维度**。FrameFlow 有 `..._FILES_BY_VERSION` /
  `..._HASHES_BY_VERSION` 两张**按版本索引**的表 + `loadVideoCreationPromptAsset(id, version)`
  + 历史资产（final-storyboard v1.0.0/v1.1.0 并存）留在磁盘。本仓 `PROMPT_TEMPLATE_VERSIONS`
  是平表，版本值**只出现在报错文案里**，`loadPromptTemplate(name)` 无版本参数，改骨架只能就地
  覆盖、旧版字节永久丢失、历史 run 无法按当时骨架复现。**且 ADR 自身不一致**：§2 G4 标准写了
  "历史版本仍可读"三条，§3 Decision 第 4 条悄悄缩成两条且未给理由。
- **D3【中·能力不对齐】不支持内联 `data:image/...;base64,` 参考图**。FrameFlow `imageFile`
  第一步就 `inlineImageFile()` 直接 base64 解成 File 不发网络（含 `MAX_GENERATION_REFERENCE_
  DATA_URL_CHARS` + 单测）；本仓 `referenceCandidates`（`newApiH3Video.ts:66-72`）只留
  `https://` 与 `/media/`，data URL 被静默丢弃。**判定：非缺陷，两种自洽策略**——本仓靠
  `generators.ts:1682` 的 `cacheGeneratedImage` 把 data URL 落盘成 `/media/`。但要留意它的三个
  原样返回分支（非匹配 scheme / 正则不匹配的 data URL / 非 http 值），进绑定即死路。
- **D4/D6【低】**：20MB 上限本仓是 `h3ReferenceMedia.ts` 本地常量（FrameFlow 是跨上传/存储/抓取
  共用的 `MAX_GENERATION_REFERENCE_BYTES`，有单测钉值），数值一致但口径变更要改多处；
  `newApiH3Video.ts:421` 成片下载仍是无界 `arrayBuffer()`，`responseMessage` 的 `response.text()`
  错误体也无界（FrameFlow `transport.ts:23` 有 64KB `boundedResponseText`）。
- **D6 反向**：本仓抓图纪律**强于** FrameFlow 三处——超时归因（区分 `TimeoutError`）、非 2xx 带
  `responseMetadata`、本地 `/media/` 的 path-traversal 守卫 + `stat` 预检大小。**别被当偏差回退。**

**复核通过的硬断言**：`boundedResponse.ts` 与 FrameFlow 逐行等价；抓图五条纪律全落地；
内容寻址贯通且抓取失败不擦指纹；`newApiH3Video.ts` 23 处 throw 无裸 `Error`；`referenceId`
去重（`shotExecutionPackage.ts:644-645`）；`VIDEOSBATCH_H3_ALLOW_HTTP` 是 9-01 引入非本轮新增
（non-goal 未破）；20MB 数值两边一致。

**待授权阶段**：P0-R（修 D1）、P2-R（修 D2）、P4（D3 裁定 + D4/D5 收口）。D1/D2 属合同级，
按 spec §7 Change Policy 必须先改 spec 再改代码，本 ADR 停在「记录 + 建议」。
**教训：ADR 里写的"标准"必须逐字覆盖到 Decision —— 我自己在 G4 上缩了一条没写理由，复审才抓到。**

## ADR-0001 优化执行 P0-R / P2-R / P4（大哥：「优化啊。」）

提交 `a7f6d49`（代码+spec+smoke）、`6649919`（ADR 执行记录）。先改 spec 再改代码。

- **D1 三处全修**：① 轮询 `H3_TASK_FAILED` 的 billingResult 由 `NOT_CHARGED` 改 `evidence.declared
  ?? "UNKNOWN"`；② 新增 `h3DeclaredBillingResult(payload)`（读裸体或 `data` 包装的
  `billing_result`/`billingResult`，**越界值忽略不强解**，只用于记账不放开自动重试）；③ 新增
  `H3ChargedEvidence` + `onCharged` 回调，经 `generators → nativeMediaStages` 落库到
  `ShotRender.videosBatchBillingResult`，让**成功路径也留下费用证据**。
- **执行中新发现的隐患（一并修）**：`onCharged` 记录失败若以普通错误逃逸 → 清掉尝试标记 → 诱导
  第二次付费提交（正是 D1 要消除的失败类）。兜法：**抛出 `H3_BILLING_RECORD_FAILED`
  （`CHARGED`、`retryable:false`、保留 taskId 与 mediaUrl）**。新码追加进 spec §8.5 允许追加清单。
- **D2**：`PROMPT_TEMPLATE_VERSION_ORDER` + `PROMPT_TEMPLATE_HASHES_BY_VERSION`（按版本索引的哈希表）
  + `promptTemplateRelativePath(name, version)`（当前→`<name>.md`，历史→`history/<name>/<version>.md`）；
  `loadPromptTemplate(name, version?)` 未登记版本 **fail-fast，绝不回退当前版本静默换指令**。
- **D4**：复核为**已满足**（20MB 单消费者、已导出、被 smoke 钉值），**不动代码**——避免为"对齐"
  而制造无意义的改动。
- **D5**：`readBoundedResponseText()`（`MAX_BOUNDED_RESPONSE_TEXT_BYTES = 64 KiB`），`responseEvidence`
  与 `responsePayload` 改有界读；**超限时"读不到载荷"必须与"读到空载荷"区分开**——返回 null 让提交
  降级成"无 taskId"从而停住重试，而不是被当成可用 JSON。
- **门禁**：`smoke:videosbatch-newapi-h3` 加 `taskFailed`/`taskFailedDeclared`/`hugeError` 三模式 +
  `onCharged` 断言；`smoke:videosbatch-prompt-templates` 加第 9 节（按版本回读、版本哈希表完整性、
  未知版本拒绝、历史路径）。`tsc --noEmit` + `verify:offline` **RC=0**。
- **D3 仍待裁定**（内联 data URL 参考图）：要么补 `inlineImageFile`（约 20 行），要么在 spec 固化
  「只接受 HTTPS 与 `/media/`」。未裁定前不动。
